# Membership settings and workflow

Admin → Settings → Membership controls the policy used for **future applications**. Sign in as an administrator and open `/admin/settings` (`https://www.ifsmhp.com/admin/settings` on the public site). Choose **Membership** in the left column. The fee fields are under **Fees & Financial Hardship**. This is not the public **Membership** item in the site menu.

Existing settings revisions, optimistic concurrency, field validation, and transactional audit records remain in use. Historical applications and outstanding OTP drafts without a policy snapshot keep the legacy requirements. Changing these settings does not reissue member IDs. The two queue review thresholds remain live settings for current applications.

## Where the application fee goes

The default fee is INR 100 for every professional type except `Student`, `School Student`, and `STEM Student (joining college)`. Those three are not charged. A recorded payment does not approve membership. An administrator still reviews the application and issues the member ID separately.

### Razorpay

Razorpay is the live way to collect an INR fee. It is on when the API process has both `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET`. The secret never goes to the browser. The checkout script receives only the key id.

- Local testing keeps the `rzp_test_…` key in the gitignored `backend/.env` on the developer machine. Those payments do not settle real money.
- Live keys start with `rzp_live_`. Put them in the API server's own `backend/.env` (`/opt/ifsmhp/backend/.env` on the IFSMHP API host), then restart the `ifsmhp-api` service. Do not commit that file, and do not put the secret in the frontend.
- After email verification, the applicant pays in Razorpay Checkout on the registration page, including by UPI. The site records the fee only when the checkout signature matches and Razorpay reports the payment captured for the same amount. A captured payment is not the same as money already in the bank. Razorpay holds it and transfers it later, on the settlement schedule, to the bank account saved under Razorpay → **Banking**. Until then, the payment is visible under Razorpay → **Transactions**. A UPI success screen from the payer's app shows the registered business name. It does not show a UPI ID, and it does not mean the HDFC account has been credited yet.
- The optional webhook is `POST /api/v1/public/razorpay/webhook`. In the Razorpay dashboard, create it with that URL and put the signing secret in `RAZORPAY_WEBHOOK_SECRET` in the same server file, then restart the API. Checkout still completes if the webhook is unset. The webhook records the same captured payment when the browser closes first.

While Razorpay is collecting the INR fee, the public policy returns `razorpayEnabled: true`, an empty `paymentInstructions`, and `upiPayment: null`. The registration page shows Razorpay and hides the bank instructions and QR code so the fee cannot be paid twice.

### Bank UPI ID and QR code

The application does not create a UPI ID. The ID belongs to the HDFC account named in the payment instructions: account name IFSMHP, account number `50200123978890`, IFSC `HDFC0000111`.

Find it in the HDFC mobile app under UPI → **Manage UPI ID** / **My UPI ID**, or in PhonePe, Google Pay, or BHIM for that same account. It looks like `name@hdfcbank`. If the account has no UPI ID, create one in the HDFC app for this account. Copy the payee name exactly as that app shows it. Payments to the ID cannot be recalled.

Enter those two values on **Settings → Membership** as **UPI ID for the payment QR code** and **UPI payee name**, then save. They take effect only when Razorpay is not configured. The registration form then shows the QR code to the right of the bank details (below them on a phone). The applicant still enters the UTR and uploads a screenshot. An administrator checks the bank credit and records the payment. Scan the QR and make one small payment before telling applicants to use it.

## Defaults and behavior

- Automatic IDs default to `IFSMHP-NNNNNN`. Admins can select manual issuance, change the uppercase prefix, or choose 4–10 sequence digits. The sequence is global and does not reset each year. IDs already stored as `PREFIX-YYYY-NNNNNN` are rewritten to `PREFIX-NNNNNN`. Manual IDs are required at approval, validated, and globally unique using the database collation. Automatic allocation skips IDs already assigned manually.
- CV (`requireProfile`) and Credentials (`CREDENTIAL`) documents remain required by default, with independent optional/required switches. `Student`, `School Student`, and `STEM Student (joining college)` may omit the CV. `School Student` may also omit the credentials document. The registration screen labels the CV upload CV, not Profile. Optional supplied files are still validated. Referrals and reference letters default to zero, with configurable counts of 0–5. Each referrer supplies a name, email, and optional organization. Letters use existing private registration uploads and their claims, up to 10 MB each.
- The application fee defaults to enabled at INR `100.00` with IFSMHP bank/UPI payment instructions. Annual dues default to disabled/zero. Currency defaults to INR, with USD and GBP also available. Enabled charges require positive amounts and payment instructions. Money is persisted as `DECIMAL(10,2)` and transported as decimal strings. Applicants whose professional type is `Student`, `School Student`, or `STEM Student (joining college)` are not charged and may be approved without a payment or waiver. When `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` are set and the charge currency is INR, the applicant pays with Razorpay Checkout after email verification. The checkout stays on the page and can open a UPI app. The server accepts the payment only when the checkout signature matches and Razorpay reports the captured amount equal to the charge. A `payment.captured` webhook to `/api/v1/public/razorpay/webhook`, signed with `RAZORPAY_WEBHOOK_SECRET`, records the same payment if the browser closes first. That records the charge as paid and does not approve membership. While Razorpay is collecting an INR fee, the admin application screen does not ask for the payer's UPI ID or a UTR. Razorpay settles the money to the bank account linked on that Razorpay account. The public policy then omits the bank instructions and the UPI QR code, so the fee is not collected twice. Without those credentials, non-student applicants enter the UTR / UPI reference and a mandatory JPEG or PNG payment screenshot on the registration form. That claim is stored on the application charge and does not settle it. **Membership approval (issuing a member ID) is blocked until the fee is paid or waived.** When a UTR claim exists, the recorded payment reference must match that claim (spaces/case ignored); update the claim first if the bank shows a different reference. Recording payment never approves membership by itself; evidence review and Approve remain separate steps. The admin queue hides quick-approve while the application fee is still outstanding.
- **UPI QR code.** `upiId` (a UPI ID such as `name@bank`) and `upiPayeeName` are optional membership settings; `upiId` ships blank. When Razorpay is not collecting the INR fee, the application fee is enabled, the currency is INR, and both are set, the registration form shows a QR code to the right of the payment instructions (below them on a phone, with a link that opens a UPI app). The server builds the `upi://pay` link from the saved UPI ID, payee name, and the application fee, so the amount is fixed in the link. The link carries no payment note, so applicants can enter the note the instructions ask for. The browser draws the QR code only when the link's payee, payee name, amount and currency equal the details printed beside it. The UPI ID is limited to letters, digits, `.`, `_`, `-` and one `@`, which leaves no character that could add a parameter to the link. Only an administrator can change it. Each change writes the usual `PlatformSettingsUpdated` audit row and a separate warning-level `PaymentDestinationChanged` row, both with the previous and new UPI ID and payee name; other administrators are not notified. The UPI settings are not copied into an application's policy snapshot, so builds without them can still read every application. The QR code settles nothing: applicants still enter the UTR and upload a screenshot, and an administrator still verifies the credit before recording payment. Applicants pay whatever UPI ID is saved, and UPI payments cannot be recalled, so confirm the ID against the bank record before saving, enter the payee name as a UPI app shows it, and make a test payment afterwards.
- A new application's policy is captured server-side when its registration OTP request is accepted. Resends and verification retain it. A stale form revision returns 409; refresh the policy while preserving the entered form and valid uploads. Older clients may omit the revision, but must satisfy the current requirements when starting a new application. Clients cannot supply policy snapshots.
- New applications require an administrator's evidence-review confirmation whenever documents/referrals/letters are required. Approval also requires the application fee to be paid or waived. Historical applications do not acquire these new approval gates.
- The application charge is created at successful OTP verification. Annual dues are first charged at approval and then on each approval anniversary, due 30 days after issuance. February 29 anniversaries become February 28 in non-leap years. Snapshot amounts and currency remain fixed; changing settings does not reprice earlier applications or enrolled members. Unpaid dues never suspend member access.
- Waivers default to disabled. When enabled for that application, the applicant/member can request a full waiver with a private reason. Admins approve or reject requests and can revoke an erroneous approval. Admins record full payments with an external transaction reference and correct mistakes by reversing the record with a reason. Original records remain in history; corrections do not undo a completed membership approval.
- Automatic archival defaults to disabled, with a default delay of 90 days (configurable 1–3,650). Only newly enrolled rejected applications with this policy enabled are eligible. Archival sets `archivedAt` without changing rejection status or deleting accounts/files/history. The member directory excludes archived applications by default and provides Archived/All filters. Restoration sets an exemption; admins can explicitly re-enable archival.

Applicants now go to `/application` after registration or OTP login. They can view their own status, payment instructions, charges, and waiver decisions, but cannot access the member dashboard. Approved members view dues and request waivers in their profile. Admin member detail includes the policy, referrals, private letter downloads, evidence review, charges, waiver decisions, and manual ID entry.

## API contracts

Existing success/error envelopes are retained. New admin endpoints require an active ADMIN and a persisted session; own-membership endpoints derive ownership from the authenticated session. Private responses use `Cache-Control: private, no-store`. Validation returns 422, stale policies/invalid transitions/duplicate IDs return 409, missing or inaccessible records return 404, and authentication/authorization use 401/403.

- `GET /api/v1/public/membership-policy`: public requirements, fees, currency, payment instructions, waiver availability, policy revision, `razorpayEnabled`, and `upiPayment`. Does not expose identity configuration, review metadata, referrals, or applicant records. `razorpayEnabled` is true only when Razorpay is configured and the currency is INR. `upiPayment` is `{ upiId, payeeName, amount, uri }`, or `null` when no QR code applies, including while Razorpay is collecting the fee. `PATCH /api/v1/admin/settings/membership` also accepts `upiId` and `upiPayeeName`; a malformed UPI ID, or a UPI ID without a payee name, returns 422.
- `POST /api/v1/membership/charges/:chargeId/razorpay`: the signed-in applicant or member starts a Razorpay order for their own unpaid INR charge. The response includes the public key id, order id, and amount in paise. It does not include the key secret.
- `POST /api/v1/membership/charges/:chargeId/razorpay/confirm`: `{ orderId, paymentId, signature }`. Records the charge only after the signature matches and Razorpay reports that payment captured for the same order and amount. Does not approve membership.
- `POST /api/v1/public/razorpay/webhook`: raw-body `payment.captured` or `order.paid` events. Accepted only when `RAZORPAY_WEBHOOK_SECRET` matches the `X-Razorpay-Signature` header.
- `PATCH /api/v1/admin/settings/membership`: existing `{ expectedRevision, values }` contract. New keys: `idIssuance`, `idPrefix`, `idPadding`, `requireProfile`, `requireCredential`, `applicationFeeEnabled`, `applicationFee`, `annualDuesEnabled`, `annualDues`, `currency`, `paymentInstructions`, `waiversEnabled`, `referralCount`, `referenceLetterCount`, `autoArchive`, `archiveAfterDays`.
- Registration `POST /api/v1/auth/otp/request`: accepts optional `policyRevision`, `referrals: [{ name, email, organization }]`, `referenceLetters: [{ fileId, claimToken }]`, and `waiverReason`. Existing `documents` kinds remain unchanged. Missing optional documents normalize to an empty list; policy validation determines required evidence.
- `GET /api/v1/membership`: the authenticated applicant/member's status and charges; never arbitrary user lookup. `POST /api/v1/membership/charges/:chargeId/payment-claims`: `{ requestId: UUID, reference }` stores an applicant UTR for matching without settling the charge. `POST /api/v1/membership/charges/:chargeId/waivers`: `{ requestId: UUID, reason }`.
- `GET /api/v1/admin/membership/:id`: admin-only policy/evidence/charge detail. The existing `GET /api/v1/admin/members/:id` also returns this as `membership`.
- `POST /api/v1/admin/membership/:id/evidence-review`: confirm required documents and references have been reviewed.
- `POST /api/v1/admin/membership/:id/charges/:chargeId/payment-claims`: admin may record/update a claimed reference the same way.
- `POST /api/v1/admin/membership/:id/charges/:chargeId/payments`: `{ requestId: UUID, reference }`; records the full charge as paid after bank verification. Does not approve membership.
- `POST /api/v1/admin/membership/:id/charges/:chargeId/corrections`: `{ recordId: paymentId, reason }`; reverses an incorrect payment record.
- `POST /api/v1/admin/membership/:id/charges/:chargeId/waivers`: `{ requestId: UUID, reason }`; an admin can record a waiver request on the member's behalf.
- `POST /api/v1/admin/membership/:id/charges/:chargeId/waiver-decision`: `{ recordId: waiverId, status: APPROVED | REJECTED | REVOKED, reason }`.
- Existing `POST /api/v1/admin/members/:id/approve` accepts optional `memberId`; it is required only for manual-policy applications. Other payload fields retain their behavior. Approved applications cannot be rejected afterward.
- `GET /api/v1/admin/members?archive=active|archived|all`: default `active` excludes archived records.
- `POST /api/v1/admin/membership/:id/restore`: `{ enableAutoArchive?: boolean }`, default false.

Amounts and currency on a charge are immutable. Repeated identical payment/waiver requests return the existing result; reusing a request ID for a different operation is rejected. Mutations lock the application **before** their first consistent read, preventing stale MySQL repeatable-read snapshots from authorizing duplicate settlements or approvals. Charge creation has an additional unique application/kind/year constraint. Settings and workflow writes roll back on audit failure. Private referral, waiver, document, payment instruction, and correction text is excluded from audit payload contents.

## Worker and deployment

The membership worker runs at startup and once per minute, uses bounded application batches, and catches up missed anniversaries for active approved accounts. Database locks and unique charge periods allow multiple API processes without duplicate charges. It logs failures, retries on its next tick, and waits for in-flight work during graceful shutdown. Set `MEMBERSHIP_WORKER_ENABLED=false` to disable it; it is automatically disabled under `NODE_ENV=test`. Tests invoke the worker directly with a controlled date. Deactivated/suspended/deleted accounts are not charged while inactive; historical periods can be caught up if their account later becomes active again.

Back up the intended database first. From the repository root:

```sh
npm --prefix backend run db:deploy
npm --prefix backend run db:generate
npm --prefix backend run build
npm --prefix frontend run build
```

If already inside `backend/`, use `npm run db:deploy` without repeating `--prefix backend`. Restart the API/worker processes with the rebuilt code and deploy the matching frontend. Migration `20261003010000_membership_policy` adds nullable policy/review/archive metadata and new evidence/charge tables. It does not rewrite historical records or enable fees, referrals, waivers, or archival. Never reset or seed an existing database. No settings initializer is required; missing keys resolve to backward-compatible defaults.
